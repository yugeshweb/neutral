# Neutral

Hybrid quantum-classical ML platform for early disease detection, built for the
*Hybrid Quantum Machine Learning Platform for Early Disease Detection* problem
statement.

> **All results in this interface are mocked.** No model is trained, no dataset
> is evaluated, and every metric is a placeholder generated by a mock runner.
> Numbers are marked as demo data wherever they appear.

## The three sections

The app opens on a launcher offering three entry points, which together trace
the workflow the problem statement asks for:

| # | Section | Covers |
|---|---------|--------|
| 01 | **Train** | Data ingestion, pre-processing, feature selection, hybrid model training |
| 02 | **Predict** | Inference workflow and model explainability |
| 03 | **Compare** | Performance evaluation and benchmarking against classical baselines |

## The pipeline

Left-to-right graph that branches into two parallel lanes after feature
selection, then converges:

| # | Stage | Lane |
|---|-------|------|
| 1 | Data Ingestion | shared |
| 2 | Cleaning & Scaling | shared |
| 3 | Feature Selection | shared |
| 4a | Baseline Training (XGBoost + RF) | classical |
| 5a | Classical Inference | classical |
| 4b | Angle Encoding | quantum |
| 5b | Variational Circuit | quantum |
| 6b | Measurement | quantum |
| 7 | Benchmark & Compare | shared |
| 8 | Explainability (SHAP) | shared |
| 9 | Results | shared |

The two lanes advance on the same tick, so they genuinely run in parallel rather
than being interleaved by a scheduler.

## Mock engine

The UI never knows it is talking to a mock. Everything goes through one
interface in [`src/lib/pipeline/runner.ts`](src/lib/pipeline/runner.ts):

```ts
export interface PipelineRunner {
  subscribe(cb: (e: PipelineEvent) => void): () => void
  start(): void
  stop(): void
  reset(): void
}
```

`createMockRunner({ speed, failAt })` walks the graph respecting dependencies,
emits incremental progress and log events, and can force any stage into an error
state so downstream nodes correctly report as blocked.

To go live, swap the one call in [`src/hooks/usePipeline.ts`](src/hooks/usePipeline.ts).
`runner.ts` carries a marked TODO block with a complete `createSSERunner`
implementation and the event contract a backend must honour. No component needs
to change.

## Data ingestion — the adapter layer

Hospital data almost never arrives as a CSV. It leaves an EHR as an HL7 v2 feed
or a FHIR bundle, a PACS as DICOM, a LIS keyed by LOINC codes, or a sequencing
run as VCF. Clinical concepts are stored as **codes, not words** — a diagnosis is
an ICD-10 code, a lab test a LOINC code — so "does this patient have diabetes" is
a code lookup, never a string match.

Every format is a different parse but the same destination: rows are patients,
columns are numeric features, one column is the label. So each is an adapter
behind one interface in [`src/lib/ingest/types.ts`](src/lib/ingest/types.ts):

```ts
export interface IngestAdapter {
  format: SourceFormat
  status: AdapterStatus
  parse(file: File): Promise<IngestResult>   // dataset + schema + notes
}
```

| Format | Source system | Codes | Status |
|---|---|---|---|
| CSV / Excel export | manual export | — | **implemented** |
| FHIR R4 Bundle | EHR / EMR | LOINC, ICD-10 | **implemented** |
| HL7 v2 message feed | EHR / EMR | LOINC | not implemented |
| DICOM study | PACS | SNOMED | not implemented |
| VCF / expression matrix | sequencing | — | not implemented |

Unimplemented formats are listed in the UI and throw a `NotImplementedError`
carrying a `requires` field stating what building them would involve. They fail
loudly and specifically rather than being hidden.

### The FHIR adapter

[`src/lib/ingest/fhir.ts`](src/lib/ingest/fhir.ts) is a real parse. It walks a
Bundle's entries, groups resources by their Patient reference, reads numeric
`Observation.valueQuantity` values keyed by LOINC code, derives a binary label
from `Condition` ICD-10 codes, and flattens to one row per patient. Sparse cells
stay empty rather than being silently zero-filled, and non-numeric observations
are counted and skipped.

FHIR R4 is worth implementing first because it is what India's **ABDM** health-
records framework is built on, and what public test servers (hapi.fhir.org,
Synthea-generated bundles) serve — so it is testable against realistic data with
no hospital agreement.

Verified against [`public/samples/sample-fhir-bundle.json`](public/samples/sample-fhir-bundle.json)
(60 patients, 602 entries) → 60 rows × 13 columns, 9 LOINC codes resolved.

**Scope, stated plainly:** it reads a Bundle *from a file*. It does not talk to a
live FHIR endpoint, do SMART-on-FHIR auth, page through `Bundle.link`, or resolve
references across bundles. This platform has **not** been run against a live
hospital or ABDM endpoint, and no such integration should be claimed for it.

### Isolated EHR validation surface

Open `/ehr-validation` while the Vite app is running to test the EHR cohort path
without changing the Train/Predict/Compare interface. It uses the existing CSV
and FHIR adapters, then calls `POST /api/validation/ehr` with the canonical CSV
they produce. The endpoint re-loads the matrix through the backend’s existing
loader, checks labels and missingness, fingerprints the input, and previews
routing against every registered neurological model. It performs no training,
inference, or diagnosis.

For Vite development, run the API and frontend in separate terminals:

```bash
PYTHONPATH=backend/src backend/.venv/bin/python -m qhealth_qml.dashboard --port 8765
VITE_QML_API_URL=http://127.0.0.1:8765 npm run dev -- --host 127.0.0.1
```

Then open `http://127.0.0.1:5173/ehr-validation`. For a built frontend, run
`npm run build`, then pass its directory to
`backend/.venv/bin/qhealth-dashboard --ui-dir dist`; the dashboard serves
`/ehr-validation` through the same SPA entry point.

## Uploads

The input panel accepts a CSV (parsed in-browser, quoted fields handled) or an
image. Images open a preview with region-of-interest markers; clicking a marker
shows its details.

Those regions are **generated from a hash of the filename**, not detected — they
are deterministic per file so demos repeat, but nothing ran on the image. The
swap point is `Finding[]` in [`src/lib/findings.ts`](src/lib/findings.ts).

Sample files live in [`public/samples/`](public/samples).

## Output

The output panel exports a run report as JSON (stage records, metrics, full log)
or the comparison table as CSV. Both carry an explicit synthetic flag and a
disclaimer field, so the marking survives outside this UI.

## Accessibility

- `prefers-reduced-motion` stops the flowing dashes, travelling dots, and marker
  blink; static state colours remain.
- Run control, node focus, and drawer dismissal are keyboard reachable; Escape
  steps back one level in the image viewer before closing it.
- Works down to 1280px, with horizontal pan below that.
